# Работа в команде EduFlow

Официальный канал — Telegram-чат проекта. Стендапы: вторник и пятница, по 15 минут. Конкретное время и часовой пояс согласуются в чате; регламент их не задаёт.

Формат сообщения к стендапу:

```text
Сделано: ...
До следующего созвона: ...
Блокеры: ... / нет
```

## Что означают команды Git

`git status` показывает изменённые файлы. `git diff` показывает изменения в содержимом. `git add` выбирает изменения для следующего коммита (staging). `git commit` сохраняет выбранный снимок **локально**. `git push` отправляет локальные коммиты на сервер. Pull Request — запрос на review и слияние ветки; сам `push` не сливает код в `develop`.

Одна ветка — одна фича или исправление. Один коммит — одно понятное, проверяемое изменение. Не нужно коммитить каждую строку, но не следует объединять несвязанные задачи в огромный коммит.

## Подключение к существующему репозиторию

Нужен установленный [Git](https://git-scm.com/install/windows). После установки перезапустите терминал, проверьте `git --version`.

Настройте автора в своём клоне (подставьте настоящие имя и email; настройки локальны для репозитория):

```powershell
git config user.name "Ваше имя"
git config user.email "ваш-email@example.com"
```

Если клона ещё нет, сначала получите URL у команды, выполните `git clone <URL_РЕПОЗИТОРИЯ> EduFlow` и перейдите в `EduFlow`. Угловые скобки — обозначение подстановки, а не часть команды. Не клонируйте поверх заполненной папки. Созданные здесь файлы перенесите в отдельную фиче-ветку существующего клона, проверяя уже имеющиеся файлы на конфликты.

В этой исходной рабочей папке не было `.git`, `develop` или удалённого репозитория. Здесь не создавались коммиты, ветки или PR. Первичную инициализацию пустого командного репозитория и базовой `develop` согласует руководитель; не создавайте независимую историю через `git init`, если у команды уже есть репозиторий.

## Обычный цикл разработки

Перед началом убедитесь, что `git status` не показывает незавершённых чужих или ваших изменений. Затем:

```powershell
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/jwt-auth
```

Если `develop` есть только на сервере, вместо `git switch develop` выполните `git switch --track origin/develop`. Новая фича создаётся от актуальной `develop`. Названия: `feature/jwt-auth`, `feature/lecture-processing`, для багов — `bugfix/refresh-token-reuse`. В `main` и `master` прямые коммиты запрещены. Работу также не ведём прямо в общей `develop`: изменения в неё попадают через PR.

После изменений и проверок из README:

```powershell
git branch --show-current
git status
git diff
# Выбирайте существующие файлы именно вашей задачи.
git add app/api/auth.py app/core/security.py tests/test_auth.py
git diff --cached
git commit -m "feat(auth): add JWT login and refresh rotation"
git push -u origin feature/jwt-auth
```

Перед `commit` проверьте имя текущей ветки и `git diff --cached`: это именно то, что сохранится. `git add` фиксирует текущее содержимое выбранного файла в staging. Если после него снова отредактировали файл, выполните `git add` повторно. `git add -p` позволяет выбрать отдельные фрагменты. Не добавляйте `.env`, токены, пароли, аудио пользователей, `.venv`, `.tools` и кэши; `.gitignore` уже подготовлен. Не используйте `git add .` без проверки состава изменений.

В примере показан коммит задачи авторизации. Для добавления всего нового бэкенда используйте отдельную ветку `feature/backend-foundation` и осмысленные коммиты по слоям, если их можно проверить отдельно. Не делайте вид, что большой бэкенд — это только JWT.

Формат сообщений — рекомендуемая командная договорённость, дополнение к регламенту:

```text
feat(lectures): add asynchronous audio upload
fix(auth): reject refresh token reuse
test(lectures): cover access to another user's lecture
docs: explain local setup and pull request workflow
chore(ci): run backend checks for develop pull requests
```

После первого `push -u` следующие коммиты в той же ветке отправляются простым `git push`. Не создавайте новую ветку для каждого замечания в PR.

## Pull Request и одобрение Руслана

На GitHub откройте **New pull request**: `base = develop`, `compare = feature/ваша-фича`. Заполните шаблон PR: что изменилось, как проверить, результаты тестов и ограничения. Добавьте Руслана в Reviewers по его настоящему аккаунту.

Если Руслан просит изменения, исправьте их в той же ветке, снова выполните проверки, `git add`, `git commit`, `git push`. PR обновится автоматически. После новых коммитов дождитесь актуального Approved. Зелёный CI и одобрение другого участника не заменяют Approved Руслана. До его одобрения слияние запрещено; кнопку Merge нажимает участник, уполномоченный командой.

Статус Done — только после QA и Design Review. Для изменения только API явно согласуйте N/A по дизайну. Шаблон PR содержит эти пункты; сам файл шаблона не обеспечивает технический запрет слияния.

Руководителю/администратору нужно включить защиту `main`, `master` (если есть) и `develop`: обязательный PR, успешный job `checks`, одобрение reviewer, сброс устаревших одобрений после новых коммитов, запрет force push и обхода правил. Для обязательного одобрения именно Руслана можно настроить `.github/CODEOWNERS` с `* @реальный-логин-Руслана` и **Require review from Code Owners**; Руслану нужны соответствующие права. Не добавлен фиктивный CODEOWNERS: логин и репозиторий неизвестны. Возможности защиты зависят от тарифа/типа репозитория; см. [GitHub: protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

После слияния и при чистой рабочей папке:

```powershell
git switch develop
git pull --ff-only origin develop
```

Удалить завершённую ветку можно через интерфейс PR. Локальное `git branch -d feature/jwt-auth` безопасно проверяет слияние, но после squash merge может отказаться: не заменяйте его автоматически на `-D`, сначала проверьте, что нужные изменения уже в `develop`.

## Если develop изменился или возник конфликт

Когда рабочая папка чистая, находясь в своей feature-ветке:

```powershell
git fetch origin
git merge origin/develop
```

При конфликте откройте перечисленные файлы, выберите правильный итоговый код и удалите маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Затем выполните проверки, добавьте исправленные файлы через `git add`, завершите `git commit` и отправьте `git push`. Если пока не можете разрешить конфликт, `git merge --abort` возвращает к состоянию перед началом merge. Это обновляет вашу ветку из `develop`, а не сливает вашу фичу в `develop`.

## Исправление ошибок в коммитах

Ошибочно добавили файл в staging, но хотите сохранить локальные изменения:

```powershell
git restore --staged путь/к/файлу
```

Для опубликованного ошибочного коммита обычно создайте исправляющий коммит или `git revert <SHA>`, затем `git push`. Не переписывайте общую историю через `reset --hard` и force push. `git restore` без `--staged` может удалить незакоммиченные правки — не используйте его как универсальную отмену.

Если секрет попал в коммит, сначала отзовите/замените его и сообщите руководителю в Telegram. Удаления файла в следующем коммите недостаточно: секрет остаётся в истории; очистку истории согласуйте с командой.
